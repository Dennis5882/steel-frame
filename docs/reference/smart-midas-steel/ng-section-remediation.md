# NG 원인 진단 · 단면 보완 — v2.3.0

> 기술 참고 · 현재 기능의 상세 규칙 (v2.3.4 기준 문서 정리, 2026-10-19). 아래 버전별 수치·시험 기록은 해당 시점의 결과입니다. 현재 지원 상태는 [현황](../current-status.md), 남은 과제는 [로드맵](../roadmap.md)을 우선 확인하세요.

## 사용 흐름

1. 모델을 생성·해석하고 설계 검토를 실행한다.
2. **설계 검토** 또는 **최적화** 단계의 `NG 원인 진단 · 단면 보완`에서 지배 부재·위치·하중조합·검토식을 확인한다. 부재력/내력과 비지지 길이, 사용성 값/한계, 접합 지배 항목도 표시한다.
3. `보완 단면 찾기`를 누르고 그룹별 후보를 선택한다. 기본 선택은 `현재 단면 유지`다. 기둥–지붕보와 스트럿–가새는 쌍으로 검토한다.
4. 선택된 변경 전체에 대한 부재·사용성·접합 NG와 최대비의 **예상값**을 확인한다.
5. `선택 단면 적용 · 재해석`으로 현재 Gen 문서 백업·모델 교체를 확인한다. 새 모델을 생성·해석하고 결과 전체를 회수해 다시 검토한다.
6. **변경 전 / 예상 / 재해석**의 세 열을 비교한다. 재분배로 새로 발생한 NG는 다음 진단에 표시되며 다시 후보를 검토할 수 있다.

후보 검토에는 연결 키가 필요하지 않으며, Gen 적용에는 유효한 키와 현재 모델·결과가 필요하다. 언어와 프로젝트 설계기준은 기존 분리 정책을 유지한다.

## 후보 탐색과 검토 범위

- TW/CN/KR의 등록 확인된 감사 카탈로그에서 역할·재료별로 필터링한다. 격리 단면과 미지원 재료는 제외하며, 성질 차이·재료 예비검토 대상은 후보에 표시한다.
- 현재와 같은 형상 종류에서 면적이 증가하고 Ix·Iy가 감소하지 않는 후보를 선택한다. 가까운 단면과 전체 범위의 분위수를 표본으로 검토한다. 그룹별 최대 5개를 제공한다.
- 우선 검토 후보는 해당 그룹의 예상 부재비·사용성비 ≤ 0.95, 구현된 기존 접합비 ≤ 1 및 검토법 차단 없음이 기준이다. 단면적 증가량을 기준으로 우선순위를 정한다. 최소중량 설계나 모든 가능한 단면의 완전 탐색을 뜻하지 않는다.
- 기둥·지붕보는 쌍별 강도·사용성과 주각/처마/마루 접합을 함께 평가한다. 스트럿·가새도 쌍으로 검토하고 가새 접합을 평가한다.
- 플랫폼 보(주보·작은보·바닥 테두리보의 공통 입력), 플랫폼 기둥, 주행보, 출입문 상부 보, 지붕 개구부 보강보는 각자의 단면 필드만 변경한다. 일반 스트럿이나 지붕보 단면에 덮어쓰지 않는다.
- 세장비·검토법 한계도 진단에 포함한다. 건물 연결부 이격·받침 초과는 외부 이동량/배치 검토로 안내하며 단면 확대로 해결했다고 표시하지 않는다.
- 선택 후 전체 조합 예상값은 다른 그룹에 남은 NG와 접합 초과도 포함한다. 후보가 없는 경우 배치·지지·하중·상세·검토법을 검토하도록 안내한다.

## 예상값과 확인값

후보 강도 검토는 현재 해석의 부재력·B2 입력을 유지하고 새 단면의 내력·비지지 길이·단면 간 영향으로 재계산한다. 사용성은 기존 단면 최적화의 라멘 강성/지붕보 처짐식, 부재 Ix 또는 가새 면적비로 환산하며 퍼린 처짐은 해당 국가의 기존 함수로 계산한다.

크레인 지지부 변위, 다경간 골조의 횡변위/지붕보 처짐, 외부 건물 이격·받침은 단면 강성만으로 환산하지 않고 기존 값을 유지한다. 이 값을 포함한 모든 예상값은 **미확인 값**으로 표시한다. 자중·정적 지진중량 증가와 부재력 재분배는 Gen 재생성·재해석에서 확인한다.

추가 구조의 전문가 검토, 냉간성형 예비검토, 추가 부재의 접합·기초·국부 상세, 연결 건물 결합 거동 등 기존 한계를 유지한다. 숫자 NG 0을 최종 설계 승인으로 표시하지 않는다. Gen 자체 국가별 강도비와의 독립 대조를 추가한 기능도 아니다.

## 상태·복원·구현

- `src/domain/remediation.ts`: 진단, 후보, 허용된 단면 필드 변경, 조합 예상, 비교 지표.
- `src/actions/remediation.ts`: 후보 생성 취소, 적용 전 확인, Gen 동일성 검사, 백업·재생성·해석·전체 검토.
- `src/components/RepairPanel.tsx`: 설계 검토/최적화 단계의 선택·비교 화면.
- `repairPlan`은 Built/Results/Design/Connections의 동일 참조를 가진 현재 결과에만 적용된다. 확인 창을 연 뒤에도 모델·입력·결과 변경을 다시 검사한다. 임의 후보 ID는 거부한다.
- 새 모델 생성·해석은 이전 후보와 비교 상태를 무효화한다. 성공 시 편집기도 새 단면으로 갱신한다. 비교는 확인한 Built/Design에만 표시한다.
- 문서 교체 직후 백업 경로를 복원 지점으로 기록한다. 실패·취소 때 `lastFail.repair`로 복원 안내를 표시하며 일반 최적화 재시도 버튼과 구분한다.
- 모델·절점 연결이 달라지는 후보는 기존 결과에 대입하지 않는다. 결과 입력 객체와 프로젝트 하중·계수·확인 상태는 수정하지 않는다.

### 라이브 실행 방법

`node --import tsx scripts/live-additions.ts --phase6 --repair-test --codes=CN`

`--codes=TW,KR`로 필요한 기준만 실행할 수 있다. 실제 앱의 `prepareRepairs`와 `applyRepairs`를 사용한다. 테스트 확인 응답기는 이 스크립트에서만 설정한다. 원본을 저장하고 종료 시 다시 열어 12개 DB 해시 일치를 확인한다. 키는 `.env`에서 읽으며 출력하거나 결과 파일에 저장하지 않는다.

각 폴더에는 기존 연동 증거, `*-repair-input.json`, `*-repair-output.json`, `*-after-repair.html`, 선택 후보와 변경 전/예상/확인 지표가 남는다. 테스트 자동 선택은 재현을 위해 각 그룹 첫 후보를 고르는 방식이며, 제품 화면에서는 사용자가 직접 선택한다.

이 결과는 테스트 샘플에 대한 앱 액션·해석·결과 완전성·수치 검토의 검증이다. 다른 프로젝트에서 첫 후보가 모든 NG를 해소한다고 보장하지 않으며, 재해석 후 다시 진단하는 흐름을 제공한다. UI 배치와 실패 복원 안내를 정리한 최종 빌드도 통과했다.
